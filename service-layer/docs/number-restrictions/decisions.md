## A – architecture (phase 2)

| ID | Topic | Decision | Status |
|---|---|---|---|
| A-1 | Indexes | Only what matters: unique `TEXT_PHONE_NUMBER` (closes the concurrency window of get-or-create), and one index by `IDNT_TRAINEE` on `AVIV_TRAINEE_RESTRICTION_NUMBER` and on `AVIV_PERMITS_FOR_RESTRICTION` (history, trainee flags). Device duplicates are prevented with `DISTINCT` in the procedure. The structural unique indexes (1:1 link, one inline row), the phone/parent/institute indexes and the device unique index were dropped as overkill. **Amended 2026-11-08:** no indexes at all, by the owner's decision. The unique index is replaced by `sp_getapplock` in the create procedure (I-13); the two trainee indexes are performance-only and can be added later without a code change. | Closed |
| A-2 | Business failure codes | Two: **400** wrong input (with the field), **409** the referenced record is no longer valid (not found, replaced, ended). 404 merged into 409. | A-3 | Structure of the save procedures | **One self-contained procedure per operation** (six procedures). A procedure never calls another. Merging create and update into a SAVE procedure was rejected (a mode switch hurts readability); building blocks orchestrated in a C# transaction were rejected in favour of one readable flow per operation. Drift mitigation: identical section headers for the repeated "new parent version" and "re-point permits" blocks, and this checklist (02-architecture.md §9). Extraction is reconsidered if a fourth copy appears (the general client). | Closed |

| A-5 | Scope wording | General restrictions are one type (`CODE_RESTRICTION_SCOPE = 1`), optionally narrowed to institutes. ## G – guidelines for phases 2 and 3

| ID | Guideline |

| G-1 | Readability and maintainability first. In procedures prefer not to split, but readable wins over unsplit. |

## I – implementation (phase 3)

Decisions the implementation had to take where the phase-2 documents left room. Code comments refer to them by ID.

| ID | Decision | Why |
|---|---|---|
| I-1 | `SP_AVIV_CREATE_TRAINEE_RESTRICTION_NUMBER` creates the trainee × number pairs in a simple `WHILE` loop over a numbered temp table. The permit create is set-based (`OUTPUT INTO`) because its rows need no per-trainee mapping afterwards. **Confirmed by the owner 2026-11-08** after reviewing the set-based alternative side by side (`MERGE … ON 1 = 0 … OUTPUT SOURCE.Seq, INSERTED.id` for the parent rows, plain `OUTPUT INTO` for the trainee and conditions rows). | Each parent row needs its own trainee row, and the parent row has no column that identifies its pair (two trainees on one number create two identical parents), so a plain `INSERT … OUTPUT` cannot return the mapping; only `MERGE` can. Both versions are equally atomic (one transaction, `XACT_ABORT`). The loop was kept for readability (G-1): the `ON 1 = 0` idiom needs explaining, `MERGE` has a known bug history and three more temp tables, and the volumes are tiny (P-12). |
| I-2 | The inline conditions row (flag = 1) copies the restriction's dates into `DATE_PERMIT_START` / `DATE_PERMIT_END`. | The columns may be `NOT NULL`, and the conditions apply over the whole restriction period. |
